# 睡眠目標・予測幅・フィードバック補正 改修設計

## 1. 目的

現行 ver1.0 の以下の問題を同時に解消する。

- 慢性的に短い実睡眠時間の中央値を「平常時100%」として扱い、翌3:15のような遅い就寝を推奨する
- 集中力低下を検証不能な単一の百分率で表示し、実測値のように見せる
- 夜に回答した「今日の調子」が、当日の夜から翌日を予測する `PREDICT#NIGHT` に誤って紐付く
- 5段階評価が保存されるだけで、次回以降の予測へ反映されない
- 評価回答後にLINE公式アカウントの汎用自動応答が返り、保存成否が分からない

本改修は成人利用者を対象とする。AASM/SRSの共同勧告に基づき、目標実睡眠時間の既定下限を7時間とする。医学的診断や治療判断には使用しない。

## 2. スコープ

### 含む

- 習慣睡眠時間と目標睡眠時間の分離
- 推奨就寝時刻、睡眠負債、基準カーブでの目標睡眠時間の利用
- 5段階評価と当日朝予測の正しい紐付け
- 少数データでも弱く働く、上限付きの個人補正
- 単一%から予測幅＋信頼度への表示変更
- 評価保存結果のLINE返信
- 既存フィードバック2件の互換読み取りと安全な補完
- LINE公式アカウントの汎用自動応答の無効化

### 含まない

- 医学的診断、疾病リスク判定
- 機械学習基盤や外部分析サービスの追加
- HRV・中途覚醒・心拍数を生理モデルの係数へ直接組み込むこと
- 7時間以外の年齢別目標の自動判定

## 3. 設計原則

1. 生理モデルの決定論的計算と文章化LLMを分離する。
2. LLMは数値、範囲、信頼度を生成せず、確定値の文章化だけを行う。
3. 習慣が短時間睡眠であっても、それを健康目標として追認しない。
4. 主観評価による補正は透明・上限付き・少数時は弱くする。
5. 元の予測値、補正値、表示範囲をDynamoDBへ保存し、後から監査可能にする。
6. 既存データを削除せず、旧形式を読み取れる後方互換性を保つ。

## 4. 習慣値と目標値

### 4.1 Baseline

`Baseline` に次の意味を持たせる。

- `wake_h`: 直近14件の起床時刻中央値。既存どおり。
- `sleep_h`: 直近14件の実睡眠時間中央値。互換性のためフィールド名を維持し、意味は「習慣値」とする。
- `target_sleep_h`: 推奨と基準カーブに使う目標実睡眠時間。

`target_sleep_h` は次式で求める。

```text
target_sleep_h = min(9.0, max(sleep_h, min_target_sleep_h))
```

- `min_target_sleep_h` の既定値は `7.0`
- 環境変数 `STC_MIN_TARGET_SLEEP_H` で `7.0`〜`9.0` の範囲に限り上書き可能
- 履歴不足時は既存既定値 `7.5` を習慣値・目標値の双方に使う

### 4.2 推奨就寝時刻

推奨候補の最遅上限を次に変更する。

```text
latest_bedtime_h = baseline.wake_h - baseline.target_sleep_h
```

既存の「起床4時間前まで」という探索上限は防御的な絶対上限として残すが、通常は目標睡眠時間の上限が先に効く。5分刻みで条件を満たす最も遅い候補を返す。

メッセージには、推奨時刻だけでなく前提を明記する。

```text
起床目安 8:40・7時間の睡眠を確保するなら、遅くとも1:40までに就寝。
```

「目標を満たせます」のような曖昧な表現は禁止する。

### 4.3 睡眠負債と基準カーブ

- 睡眠負債の不足量は `target_sleep_h - actual_duration_h` で計算する
- 比較対象となる基準カーブも `target_sleep_h` の実睡眠を使う
- 習慣値 `sleep_h` はコンテキストと信頼度判定にのみ使う

これにより、5時間24分が習慣であっても、それを0%低下の理想状態にはしない。

## 5. 5段階評価の正しい紐付け

### 5.1 日付の意味

夜22:30の質問「今日の調子はどうだった？」は、その日の朝に送った予測を評価する。

例:

- 起点日 `2026-08-26` の睡眠 → `PREDICT#MORNING/2026-08-26` → 8月27日の状態を予測
- 8月27日22:30の評価 → `evaluated_date=2026-08-27`, `prediction_date=2026-08-26`

評価を当日の `PREDICT#NIGHT` に紐付けてはならない。

### 5.2 Feedbackスキーマ

`FEEDBACK` のSKは評価対象日 `evaluated_date` とする。

```text
date             互換フィールド。evaluated_dateと同値
evaluated_date   実際に評価した日
prediction_date  対応するPREDICT#MORNINGの起点日
score            1〜5
answered_at      ISO 8601 JST
```

旧レコードに `evaluated_date` / `prediction_date` がない場合は、`date` を評価対象日、`date - 1日` を予測日として読み取る。ただし対応する朝予測が存在する場合だけ補正学習へ採用する。

### 5.3 Webhook解決規則

- 評価回答時刻から直近2日分の夜質問日を探索する
- 対応する `PREDICT#MORNING/(質問日-1日)` が存在し、未回答なら保存する
- 同じ評価対象日に再回答した場合は最新値で上書きする
- 対応予測がなければ学習データとして保存せず、その旨をLINE返信する

## 6. 個人補正

### 6.1 主観評価の代理低下率

5段階評価を次の代理低下率へ変換する。これは医学的尺度ではなく、補正専用の順序尺度である。

| 評価 | 意味 | 代理低下率 |
|---:|---|---:|
| 5 | 絶好調 | 0% |
| 4 | やや良い | 7.5% |
| 3 | ふつう | 15% |
| 2 | 悪い | 22.5% |
| 1 | 最悪 | 30% |

各有効評価について、対応する朝予測の主要時間帯平均値との差を求める。

```text
residual = subjective_drop_pct - predicted_mean_drop_pct
```

### 6.2 集約と縮小

- 直近30件を新しい順に使用
- 新しい順の重みを `0.9^i` とする
- 加重平均残差を求める
- 少数データの縮小係数を `n / (n + 7)` とする
- 最終補正値を `-15`〜`+15`ポイントへクランプする

```text
calibration_offset = clamp(weighted_mean_residual * n/(n+7), -15, +15)
```

1件目から弱く反映され、件数が増えるほど本人の評価を強く反映する。

### 6.3 適用先

- 夜の各就寝候補の主要時間帯平均低下率
- 朝の集中力低下カーブ

補正前の値も保存する。気分カーブはREM由来の別指標であるため、本補正を直接適用しない。

## 7. 予測幅と信頼度

### 7.1 信頼度

有効な睡眠履歴件数と有効な評価ペア件数から決める。

| 信頼度 | 条件 | 表示マージン |
|---|---|---:|
| 低 | 睡眠履歴7件未満、または評価7件未満 | ±5ポイント |
| 中 | 睡眠履歴7件以上、評価7〜29件 | ±3ポイント |
| 高 | 睡眠履歴14件以上、評価30件以上 | ±2ポイント |

条件が複数にまたがる場合は低い方を採用する。

### 7.2 表示範囲

補正後中心値 `p` とマージン `m` から次を作る。

```text
lower = clamp(round(p - m), 0, 100)
upper = clamp(round(p + m), 0, 100)
```

表示例:

```text
9時台　低下見込み 3〜13%
信頼度：低（評価データ2件）
※睡眠モデルと主観評価による推定幅で、実測の仕事能力ではありません。
```

単一の `-8%` や「平常時100%」は使わない。内部の意思決定には補正後中心値を使う。

## 8. LINE返信

### 8.1 アプリからの返信

Webhookイベントの `replyToken` を使い、Messaging APIのreply endpointから返信する。

保存成功:

```text
評価1を記録しました。次回以降の予測補正に反映します。
```

対応予測なし:

```text
評価を対応する朝の予測に紐付けられませんでした。次の夜の評価から記録します。
```

返信失敗でWebhook全体を再実行して評価を重複処理しないよう、評価保存を冪等にした上で、返信失敗はログとメトリクスへ記録する。

### 8.2 LINE公式アカウント設定

- LINE Official Account Managerの「応答メッセージ」を無効化する
- Chatが自動応答を生成する設定も無効化する
- Webhookは有効のまま維持する
- 変更後に評価クイックリプライを1回送り、汎用文が返らずSleepTechの確認文だけ返ることを確認する

## 9. データ保存

`Prediction` に以下を追加する。

```text
raw_mean_drop_pct       補正前中心値
calibrated_mean_drop_pct 補正後中心値
range_low_pct           表示下限
range_high_pct          表示上限
confidence              low / medium / high
feedback_count          補正に使った件数
calibration_offset_pct  適用した補正値
```

既存の `mean_drop_pct` は後方互換のため残し、補正後中心値を格納する。旧レコードは追加フィールドなしでも読めること。

## 10. エラー処理と監査

- 不正な評価値は保存も返信もしない
- 対応予測欠損は `feedback_unmatched` として記録
- 補正計算で不正レコードを見つけた場合はそのレコードだけ除外
- 補正値、利用件数、信頼度を夜・朝ログへ出す
- LINE返信の成功・失敗を別イベントで記録
- LLMガードレールは時刻、範囲の両端、睡眠時間、信頼度の改変を拒否する
- LLMが失敗した場合も同じ確定値をテンプレート文で送る

## 11. 移行

1. 現在の`FEEDBACK`全件を強整合読み取りでバックアップ確認する。
2. 旧レコードごとに`evaluated_date=date`、`prediction_date=date-1日`を補完する。
3. 対応する`PREDICT#MORNING`がないレコードは削除せず、補正対象外として残す。
4. 条件付き更新で、回答時刻・スコアが変わっていない場合だけ補完する。
5. 更新前後の件数、採用件数、対象外件数を記録する。

## 12. テストと受け入れ条件

### モデル

- 習慣睡眠5時間24分・起床8:41でも、7時間未満を確保する3:15を推奨しない
- 同条件の最遅上限が概ね1:41となり、5分刻みの推奨が1:40以前になる
- 睡眠負債と基準カーブが目標睡眠時間を使う
- 7〜9時間の設定境界を検証する

### 補正

- 評価1件から縮小された非ゼロ補正が適用される
- 30件より古い評価は使わない
- 補正が±15を超えない
- 旧形式、欠損、対応予測なしを安全に除外する
- 補正前後と範囲がDynamoDBへ保存される

### LINE

- 夜質問日の前日に対応する朝予測へ評価が紐付く
- 保存成功時に確認返信が1回だけ届く
- LINE公式アカウントの汎用自動応答が届かない
- 1〜5以外は取り込まない

### 表示

- 夜・朝とも単一%ではなく範囲を表示する
- 信頼度と評価件数を表示する
- 「平常時100%」「目標を満たせます」を使用しない
- 実測能力ではない旨を必ず表示する

### 回帰・デプロイ

- 全pytest成功
- `compileall`成功
- `cdk synth --strict`成功
- `cdk diff`に既存リソースの削除・置換がない
- 実機LINE、DynamoDB、CloudWatchで夜・朝・評価の一連フローを確認する

## 13. ロールアウト

1. コードとテストをLuna（中エフォート）で実装する。
2. Sol（中エフォート）で数式、日付紐付け、後方互換、LINE冪等性をレビューする。
3. CDK差分を確認してAWSへデプロイする。
4. 既存フィードバックを条件付き補完する。
5. LINE公式アカウントの自動応答を無効化する。
6. テスト用評価を1回送り、保存・返信・補正値を確認する。
7. 夜・朝の通知を手動実行し、推奨時刻と予測幅を確認する。
