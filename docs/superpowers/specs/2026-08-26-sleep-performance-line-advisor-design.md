# 設計仕様: 睡眠→翌日パフォーマンス予測 LINE アドバイザー

- 日付: 2026-08-26
- プロジェクト: 260826_SleepTech_ver1.0
- リポジトリ: https://github.com/masanori-takada/260826_SleepTech_ver1.0 (private)
- 転用元: 260725_Night_Ramen_Breakdown_ver1.4

## 1. 目的

1日2回の LINE 通知で、睡眠と翌日パフォーマンスの因果を本人に見える形にし、行動を変える。

- **夜 22:30**: 「今夜◯時までに寝れば、明日はベスト比 -◯% 以内」という推奨就寝時刻を1つ提示する。
- **朝 8:00**（または「おはよう」で前倒し）: 前夜の実測睡眠から、今日の時間帯別パフォーマンス低下カーブと、それを緩和するリカバリー行動（カフェイン・光曝露）を提示する。

対象指標は **認知・仕事の集中力** と **気分・メンタルの安定** の2軸。

## 2. スコープ

### ver1.0 に含む

- Two-Process Model による決定論的なパフォーマンス予測
- 個人ベースライン（起床時刻・睡眠時間）の自動算出
- カフェイン時刻／光曝露時刻の決定論的算出
- OpenAI API による文章化（数値生成は一切させない）
- ガードレール検証
- LINE 送信（夜のクイックリプライによる5段階フィードバック収集）
- 収集した5段階評価の蓄積（利用は ver2）

### ver1.0 に含まない

- 個人回帰によるモデル係数のキャリブレーション（ver2）
- Google カレンダー連携による明日の予定からの逆算
- 仮眠の提案
- 重要業務のスケジューリング提案
- ラーメン断ち関連の全機能（転用元から削除）

## 3. 前提と確定した意思決定

| 項目 | 決定 | 理由 |

| インフラ | AWS 継続（Supabase は採用しない） | CDK/DynamoDB/Scheduler/Secrets が既に組み上がっており、移行の利得が工数に見合わない |

| 予測方式 | Two-Process Model（決定論的）→ ver2 で個人フィット | 初日から数字が出る。同一入力で必ず同一出力 |
| 夜の見せ方 | 推奨就寝時刻を1つだけ | 迷いを作らない |
| 夜の送信時刻 | 22:30 JST 固定 | 推奨就寝（24時前後）の約90分前。行動を変える余裕がある |
| 起床時刻の決定 | Fitbit 実績の中央値（直近14日）＋設定で上書き | 初日から動き、生活変化に追従する |

| 朝の提案内容 | カフェイン時刻・量／光曝露 | 決定論的に時刻算出でき、エビデンスが強い |
| フィードバック | 夜のメッセージ末尾にクイックリプライ1問（5段階） | 通知を1日2回に保つ。タップ1回で完了 |
| LINE チャネル | SleepTech 用を新規作成 | Webhook URL は1チャネル1つ。既存と共用すると衝突する |
| Google 認証 | 既存リフレッシュトークンを新 Secrets にコピー | 同一 Google Cloud プロジェクト・同一スコープ。OAuth 同意フローの再実施を回避 |
| 既存システム | Night Ramen をすぐ停止 | 通知過多とデータ取得の二重化を避ける |

**Lambda の依存は boto3 + 標準ライブラリのみ。** OpenAI SDK は導入せず `urllib.request` で HTTPS を叩く。デプロイパッケージが軽く、Lambda Layer の管理が不要になる（転用元の設計方針を踏襲）。

### AWS リソース

| リソース | 用途 |
|---|---|
| Lambda `NightFn` | 22:30 の夜フロー |
| Lambda `MorningFn` | 8:00 の朝フロー |
| Lambda `WebhookFn` | LINE Webhook（起床トリガー・5段階回答の受信） |
| EventBridge Scheduler ×2 | 夜 22:30 JST / 朝 8:00 JST |
| DynamoDB `SleepTechTable` | バイタル・予測・メッセージ・フィードバック・設定 |
| Secrets Manager ×3 | `sleeptech/google-oauth`, `sleeptech/line`, `sleeptech/openai` |

### データフロー（夜）

1. 直近14日のバイタルを DynamoDB から取得
2. `baseline` が起床時刻中央値・平常時睡眠時間・HRV 基準値を算出
3. `two_process` が二分探索で推奨就寝時刻を解く
4. `llm` が確定数値を受け取り日本語文章に整形
5. `guardrail` が検証（不通過なら最大2回再生成、それでも駄目ならテンプレート文）
6. LINE 送信（クイックリプライ付き）、冪等フラグを立てる
7. 予測とメッセージを DynamoDB に保存

### データフロー（朝）

1. Google Health API から前夜の睡眠・HRV・皮膚温等を取得
2. DynamoDB に保存
3. `two_process` が今日の時間帯別低下カーブを算出
4. `recovery` がカフェイン時刻・量と光曝露時刻を算出
5. `llm` が文章化 → `guardrail` → LINE 送信

## 5. 予測モデル（model/two_process.py）

### Process S（恒常性睡眠圧）

```
覚醒中: S(t) = 1 - (1 - S0) * exp(-t / TAU_RISE)     TAU_RISE  = 18.2h
睡眠中: S(t) = S0 * exp(-t / TAU_DECAY)              TAU_DECAY = 4.2h
```

### Process C（概日リズム）

午後の谷を再現するため2次高調波を加える。

```
C(t) = A * [ sin(2*pi*(t - phi) / 24) + 0.2 * sin(4*pi*(t - phi) / 24) ]
```

位相 `phi` は個人の起床時刻中央値から推定する（体温最低点＝覚醒度の底は起床の約2時間前に位置するという関係を用いる）。

### 覚醒度と2本のカーブ

```
alertness(t) = C(t) - S(t)
```

- **集中力カーブ** = `alertness(t)`
- **気分カーブ** = `alertness(t) - W_REM * (REM不足 + 深睡眠不足の正規化値)`

睡眠不足時の情動不安定は REM 不足の寄与が大きいため、気分カーブでは REM／深睡眠の不足に追加の重み `W_REM` を課す。

### %への変換

「個人ベースラインの睡眠時間を確保した場合」のカーブを 100% の基準線とし、実際（朝）または予定（夜）の睡眠でのカーブとの差を時間帯ごとに % 化する。

**この % は絶対的な能力値ではなく、本人の平常時を 100% とした相対値である。** この定義をメッセージ本文に必ず明記する。

### 睡眠負債の持ち越し

直近7日の睡眠不足を減衰加重（当日の重みが最大）で積算し、Process S の初期値 `S0` に加算する。連続した寝不足が数字に反映される。

### 推奨就寝時刻の解法

「明日の主要時間帯（起床 +2h 〜 起床 +10h）の平均低下率が閾値以内に収まる、最も遅い就寝時刻」を二分探索で求める。閾値の既定は 10%（`STC_TARGET_DROP_PCT` で変更可能）。

### モデルの限界（明示すること）

これは母集団の生理モデルであり、本人の実測ではない。ver1.0 の % は目安である。この旨をメッセージ文面に含め、ガードレールで断定表現を弾く。夜のクイックリプライで蓄積した5段階評価が30日分たまった時点で、ver2 において係数を個人フィットさせる。

## 6. リカバリー算出（model/recovery.py）

### カフェイン

- 半減期を 5 時間として体内残存量をモデル化
- 今夜の推奨就寝時刻において残存量が閾値未満になる **最終摂取可能時刻** を算出
- 低下カーブの谷の手前に摂取タイミングを配置（通常は午前1回＋昼1回の2分割）

### 光曝露

- 起床後30分以内の屋外光曝露を推奨（概日位相の前進）
- 就寝の約3時間前から高照度・ブルーライトの回避を推奨
- 時刻はすべて個人の起床時刻・推奨就寝時刻から算出する

## 7. LLM の扱い（llm/）

- 呼び先: `POST https://api.openai.com/v1/chat/completions`（`urllib.request`）
- モデル: `LLM_MODEL` 環境変数。**既定値は暫定であり、実機確認時に正しい文字列へ差し替える**
- APIキー: Secrets Manager `sleeptech/openai`
- 役割: **確定した数値・時刻を日本語の文章に整形することのみ。** プロンプトに数値を埋め込み、変更を禁じる
- 温度: 0.7（表現の変化のため）。数値はプロンプト内の確定値であり温度の影響を受けない

### 障害時フォールバック（設計要件）

1. タイムアウトまたはエラー時は2回リトライ
2. なお失敗する場合、Python が保持する数値からテンプレート文を組んで送信する

**LLM が落ちても、推奨就寝時刻とリカバリー時刻は必ず届く。** モデルIDが未確定のまま実装を進める以上、この経路は必須である。

## 8. ガードレール（guardrail/validator.py）

転用元の正規表現ベース検証を移植し、本プロジェクト向けに検査項目を差し替える。

| 検査 | 内容 |
|---|---|
| 医療断定 | 「診断」「治療」「病気です」等の医学的断定を弾く |
| 過度な不安煽り | 「取り返しがつかない」「寿命が縮む」等を弾く |
| 断定表現 | 「必ず」「確実に」＋% の言い切りを弾く（目安である旨の併記を必須とする） |
| 数値改変 | プロンプトで指示した数値・時刻が本文に正しく現れているかを照合。改変を検出したら再生成 |
| 人格否定 | 転用元の検査をそのまま維持 |

不通過時は最大2回まで再生成し、それでも通らなければ安全なテンプレート文へフォールバックする。

## 9. データモデル（DynamoDB）

単一テーブル設計。パーティションキー `pk`、ソートキー `sk`。

| エンティティ | pk | sk | 内容 |
|---|---|---|---|
| 日次バイタル | `VITAL#<date>` | `META` | 睡眠時間・深睡眠・REM・中途覚醒・HRV・皮膚温・呼吸数・夜間平均HR・体重 |
| 予測 | `PREDICT#<date>` | `NIGHT` / `MORNING` | 推奨就寝時刻、時間帯別低下率、リカバリー時刻 |
| メッセージ | `MSG#<date>` | `NIGHT` / `MORNING` | 本文、ガードレール結果、再生成回数、送信可否 |
| フィードバック | `FEEDBACK#<date>` | `META` | 5段階評価、回答時刻 |
| 設定 | `CONFIG` | `META` | 起床時刻の上書き値、目標低下率閾値 |
| 冪等フラグ | `IDEM#<date>` | `NIGHT` / `MORNING` | 送信済みフラグ |

バイタルの保持期間は 365 日（TTL）。フィードバックは ver2 の学習に使うため無期限。

## 10. エラー処理

| 事象 | 挙動 |
|---|---|
| Google Health 取得失敗・睡眠データ欠損 | **予測 % を一切出さない。** データ欠損である旨と一般的アドバイスのみ送信 |
| OpenAI API 障害 | 2回リトライ後、テンプレート文で送信（数値は保持されている） |
| 同意失効（`ConsentRevokedError`） | 収集を停止し、再認証を促す通知を送る |
| ガードレール不通過 | 最大2回再生成 → 安全なテンプレート文 |
| 二重実行 | `IDEM#<date>` + スロット（night/morning）で冪等制御 |

## 11. テスト

優先順位の高い順。

1. **ガードレール** — 医療断定・不安煽り・数値改変の検出（最優先・NON-NEGOTIABLE）
2. **`two_process`** — 境界値、単調性（睡眠が短いほど低下率が大きい）、既知入力に対する期待値、二分探索の収束
3. **`recovery`** — カフェイン最終摂取時刻の境界、光曝露時刻の算出
4. **LLM 障害時フォールバック** — API 失敗時にテンプレート文が送信されること
5. **`baseline`** — 起床時刻中央値、データ不足時の既定値
6. **統合（夜／朝）** — フェイク注入による end-to-end

`model/` 配下は純粋関数のみで構成し、AWS も LLM も使わずにテストできる状態を保つ。
