# 設計仕様: 睡眠→翌日パフォーマンス予測 LINE アドバイザー

- 日付: 2026-08-26
- プロジェクト: 260826_SleepTech_ver1.0
- リポジトリ: https://github.com/masanori-takada/260826_SleepTech_ver1.0 (private)
- 転用元: 260725_Night_Ramen_Breakdown_ver1.4

## 1. 目的

1日2回の LINE 通知で、睡眠と翌日パフォーマンスの因果を本人に見える形にし、行動を変える。

- **夜 22:30**: 「今夜◯時までに寝れば、明日はベスト比 -◯% 以内」という推奨就寝時刻を1つ提示する。
- **朝 8:00**（または「おはよう」で前倒し）: 前夜の実測睡眠から、今日の時間帯別パフォーマンス低下カーブと、それを緩和するリカバリー行動（カフェイン・光曝露）を提示する。

対象指標は **認知・仕事の集中力** と **気分・メンタルの安定** の2軸。

## 2. スコープ

### ver1.0 に含む

- Two-Process Model による決定論的なパフォーマンス予測
- 個人ベースライン（起床時刻・睡眠時間）の自動算出
- カフェイン時刻／光曝露時刻の決定論的算出
- OpenAI API による文章化（数値生成は一切させない）
- ガードレール検証
- LINE 送信（夜のクイックリプライによる5段階フィードバック収集）
- 収集した5段階評価の蓄積（利用は ver2）

### ver1.0 に含まない

- 個人回帰によるモデル係数のキャリブレーション（ver2）
- Google カレンダー連携による明日の予定からの逆算
- 仮眠の提案
- 重要業務のスケジューリング提案
- ラーメン断ち関連の全機能（転用元から削除）

## 3. 前提と確定した意思決定

| 項目 | 決定 | 理由 |
|---|---|---|
| 実装形態 | 別リポジトリで新規構築、既存からコード転用 | 関心の分離。ラーメン機能を引きずらない |
| インフラ | AWS 継続（Supabase は採用しない） | CDK/DynamoDB/Scheduler/Secrets が既に組み上がっており、移行の利得が工数に見合わない |
| LLM | OpenAI 本家 API（api.openai.com） | 指定 |
| モデルID | `LLM_MODEL` 環境変数。既定値は暫定 | 「GPT5.6 luna」の正確な API 文字列が未確認。差し替え点を1箇所に閉じ込める |
| 予測方式 | Two-Process Model（決定論的）→ ver2 で個人フィット | 初日から数字が出る。同一入力で必ず同一出力 |
| 夜の見せ方 | 推奨就寝時刻を1つだけ | 迷いを作らない |
| 夜の送信時刻 | 22:30 JST 固定 | 推奨就寝（24時前後）の約90分前。行動を変える余裕がある |
| 起床時刻の決定 | Fitbit 実績の中央値（直近14日）＋設定で上書き | 初日から動き、生活変化に追従する |
| 朝の送信 | 8:00 JST 固定＋「おはよう」で前倒し | 既存 Feature 003 の起床トリガー実装を転用 |
| 朝の提案内容 | カフェイン時刻・量／光曝露 | 決定論的に時刻算出でき、エビデンスが強い |
| フィードバック | 夜のメッセージ末尾にクイックリプライ1問（5段階） | 通知を1日2回に保つ。タップ1回で完了 |
| LINE チャネル | SleepTech 用を新規作成 | Webhook URL は1チャネル1つ。既存と共用すると衝突する |
| Google 認証 | 既存リフレッシュトークンを新 Secrets にコピー | 同一 Google Cloud プロジェクト・同一スコープ。OAuth 同意フローの再実施を回避 |
| 既存システム | Night Ramen をすぐ停止 | 通知過多とデータ取得の二重化を避ける |

## 4. アーキテクチャ

```
src/sleeptech/
  collectors/    google_health_api.py, google_auth_helper.py   # ほぼそのまま移植
  memory/        schemas.py        # 再定義
                 dynamo_backend.py # 新規実装（既存は日付範囲クエリ不可のため流用不能）
                 client.py         # 新規実装
  model/         two_process.py    # %予測の中核。純粋関数。LLM 不使用
                 baseline.py       # 直近14日から起床時刻・睡眠時間の個人基準
                 recovery.py       # カフェイン／光曝露の時刻算出
  llm/           client.py         # OpenAI Chat Completions を urllib で呼ぶ
                 prompts.py        # 確定数値を埋め込み「言い換えのみ」を厳命
  guardrail/     validator.py      # 構造を踏襲し検査項目は全面差し替え
                 fallback.py       # 新規（テンプレート文）
  notifier/      line.py           # push/冪等の構造を踏襲、送信内容は再実装
  workflow/      night.py, morning.py                          # 新規
  observability.py                                             # そのまま移植
src/handlers/    night_handler.py, morning_handler.py, webhook_handler.py
infra/           SleepTechStack
tests/           unit/ integration/
```

**転用の実態を正確に書いておく。** そのまま移植できるのは `collectors/`（Google Health API クライアント・OAuth ヘルパー）と `observability.py` のみ。`guardrail/` `notifier/` `memory/` `workflow/` はファイル構成とパターンを踏襲するが、中身はラーメン固有の前提（説得戦略の自律更新、2択の食べた/我慢した、話題ローテーション）が深く埋め込まれているため実質は再実装になる。実装フェーズの見積りはこれを前提とする。

**Lambda の依存は boto3 + 標準ライブラリのみ。** OpenAI SDK は導入せず `urllib.request` で HTTPS を叩く。デプロイパッケージが軽く、Lambda Layer の管理が不要になる（転用元の設計方針を踏襲）。

### AWS リソース

| リソース | 用途 |
|---|---|
| Lambda `NightFn` | 22:30 の夜フロー |
| Lambda `MorningFn` | 8:00 の朝フロー |
| Lambda `WebhookFn` | LINE Webhook（起床トリガー・5段階回答の受信） |
| EventBridge Scheduler ×2 | 夜 22:30 JST / 朝 8:00 JST |
| DynamoDB `SleepTechTable` | バイタル・予測・メッセージ・フィードバック・設定 |
| Secrets Manager ×3 | `sleeptech/google-oauth`, `sleeptech/line`, `sleeptech/openai` |

### データフロー（夜）

1. 直近14日のバイタルを DynamoDB から取得
2. `baseline` が起床時刻中央値・平常時睡眠時間・HRV 基準値を算出
3. `two_process` が線形スキャンで推奨就寝時刻を解く
4. `llm` が確定数値を受け取り日本語文章に整形
5. `guardrail` が検証（不通過なら最大2回再生成、それでも駄目ならテンプレート文）
6. LINE 送信（クイックリプライ付き）、冪等フラグを立てる
7. 予測とメッセージを DynamoDB に保存

### データフロー（朝）

1. `IDEM#MORNING` / `<date>` を確認。送信済みなら即終了
2. Google Health API から前夜の睡眠・HRV・皮膚温等を取得
3. DynamoDB に保存
4. `two_process` が今日の時間帯別低下カーブを算出
5. `recovery` がカフェイン時刻・量と光曝露時刻を算出
6. `llm` が文章化 → `guardrail` → LINE 送信 → 冪等フラグを立てる

**この朝フロー全体を1つの関数 `run_morning(date, deps)` に閉じ、`MorningFn`（8:00 定時）と `WebhookFn`（「おはよう」検出時）の両方から呼ぶ。** 転用元は webhook 側でデータ収集のみを先行実行し、送信は 8:00 に無条件で行う設計（冪等チェックなし）だった。本プロジェクトでは送信内容が重いため、その設計をそのまま持ち込むと二重送信になる。冒頭の冪等チェックと末尾のフラグ設定を `run_morning` 内に置くことで、どちらの Lambda から呼ばれても1日1回に収束させる。

### 日付の規約

**すべての `<date>` は「その夜の起点となる日（＝夜メッセージの送信日）」を指す。** タイムゾーンは JST 固定。

- 夜 22:30 に送るメッセージの `<date>` = その日の日付
- 翌朝 8:00 に送るメッセージの `<date>` = **前夜と同じ日付**（起床日ではない）
- したがって `PREDICT#NIGHT` と `PREDICT#MORNING` の同一 `<date>` は必ず同じ晩を指す
- 日付をまたぐ就寝時刻は内部では「起点日 24:00 からの経過分」として扱い、24 時以降は表示上「翌 0:30」の形式にする（「24:30」とは書かない）
- Google Health の睡眠レコードは `sleep.interval.endTime`（起床側）のローカル日で選択される（転用元 `_pick_sleep_for_date` の実装）。本プロジェクトの `<date>` は起点日なので、**保存時に「起床日 − 1日」に変換する**。ここを取り違えると全レコードが1日ずれる

### 睡眠レコードから追加で取り出す項目

転用元の `_derive_sleep_metrics` は総睡眠時間・深睡眠・中途覚醒のみを派生している。本プロジェクトでは以下を追加で抽出する。

| 項目 | 取得元 | 用途 |
|---|---|---|
| `rem_sleep_min` | STAGES の `type == "REM"` の合計 | 気分カーブの `W_REM` 補正 |
| `bedtime` | `sleep.interval.startTime` + `startUtcOffset` | 実績就寝時刻 |
| `wake_time` | `sleep.interval.endTime` + `endUtcOffset` | **`baseline` の起床時刻中央値。これが無いと推奨就寝時刻を逆算できない** |

`sleep_score` は STAGES データ型に含まれないため常に `None`。本プロジェクトでは使用しない。

## 5. 予測モデル（model/two_process.py）

### Process S（恒常性睡眠圧）

```
覚醒中: S(t) = 1 - (1 - S0) * exp(-t / TAU_RISE)     TAU_RISE  = 18.2h
睡眠中: S(t) = S0 * exp(-t / TAU_DECAY)              TAU_DECAY = 4.2h
```

### Process C（概日リズム）

午後の谷（post-lunch dip）を再現するため、12時間周期の第2項を加える。

```
C(t) = -A * cos(2*pi*(t - t_min) / 24) - A * H * cos(2*pi*(t - t_dip) / 12)

t_min = 起床時刻 - 2h   （覚醒度の底＝体温最低点）
t_dip = 起床時刻 + 8h   （午後の谷）
```

第1項は `t_min` で最小、その12時間後に最大となる。第2項が `t_dip` に副次的な谷を作る。単純な正弦波では午後の谷が現れず「14-16時が最も落ちる」という体感を再現できないため、この形を採る。

### 覚醒度と2本のカーブ

```
alertness(t) = C(t) - S(t)
```

- **集中力カーブ**: `alertness(t)`
- **気分カーブ**: `alertness(t) - W_REM * rem_deficit_ratio`
  - `rem_deficit_ratio = max(0, (平常時REM - 実績REM) / 平常時REM)`
  - REM が取得できない日は深睡眠で代替し、どちらも欠損なら気分カーブ＝集中力カーブとする

### %への変換

**覚醒度から % への変換は線形ではなくシグモイドを通す。**

```
perf(t)     = 1 / (1 + exp(-K * (alertness(t) - THETA)))
drop_pct(t) = clamp(0, 100, (perf_base(t) - perf_actual(t)) / perf_base(t) * 100)
```

`perf_base` は「平常時の睡眠時間を確保した場合」のカーブ。線形の差分ではなくシグモイドを通す理由は、**覚醒度が低い領域（午後の谷）でこそ睡眠不足の差が増幅される**という実感を再現するためである。線形差分だと時間帯によらずほぼ一定の % になり、「14-16時が谷」が出ない。

**この % は絶対的な能力値ではなく、本人の平常時を 100% とした相対値である。** この定義をメッセージ本文に必ず明記する。

### パラメータ確定値

`model/constants.py` に集約する。`TAU_RISE` / `TAU_DECAY` は Borbély/Achermann 系 Two-Process Model の標準的な値。それ以外は第11節の出力レンジ検査を満たすよう決めた値である。

| 定数 | 値 | 意味 |
|---|---|---|
| `TAU_RISE` | 18.2 | 覚醒中の睡眠圧上昇時定数（時間） |
| `TAU_DECAY` | 4.2 | 睡眠中の睡眠圧減衰時定数（時間） |
| `CIRCADIAN_AMPLITUDE` (A) | 0.25 | 概日リズム振幅 |
| `HARMONIC_RATIO` (H) | 0.5 | 午後の谷の相対的深さ |
| `PERF_STEEPNESS` (K) | 6.0 | シグモイドの傾き |
| `PERF_THRESHOLD` (THETA) | -0.3 | シグモイドの中心 |
| `W_REM` | 0.08 | 気分カーブの REM 不足重み |

この値での期待出力（起床 7:00、平常時睡眠 7.5h、前日負債なし）は次のとおり。第11節の検査はこの表を基準とする。

| 実際の睡眠 | 10時の低下率 | 14時の低下率 |
|---|---|---|
| 7.5h | 0% | 0% |
| 6h | -10% | -12% |
| 5h | -20% | -22% |

（2026-08-26 出荷前レビュー C3/I8 対応で実測値に更新。以前の表は実装との乖離が
`test_drop_is_within_plausible_range` のレンジ 5〜20 の広さで隠れていた。）

いずれも午後の方が落ち込みが大きいこと、8h 以上で 0% に張り付くことを検査する。

### 睡眠負債の持ち越し

直近7日の睡眠不足を減衰加重（当日の重みが最大）で積算し、Process S の初期値 `S0` に加算する。連続した寝不足が数字に反映される。

### 推奨就寝時刻の解法

「明日の主要時間帯（起床 +2h 〜 起床 +10h）の平均低下率が閾値以内に収まる、最も遅い就寝時刻」を求める。閾値の既定は 10%（`STC_TARGET_DROP_PCT` で変更可能）。

**二分探索は単調性を前提とするが、Two-Process Model は Process C の位相との相互作用で局所的に単調性を失いうる。** そのため探索は二分法ではなく、**探索区間を5分刻みで走査する線形スキャン**とする。区間は「現在時刻」から「起床予定の4時間前」まで。1晩あたり最大 200 点程度の評価であり、純粋関数のためコストは無視できる。単調性を仮定しないので局所的な逆転があっても誤った解に収束しない。

境界ケースを明示的に扱う。

| ケース | 挙動 |
|---|---|
| 全区間で閾値を超える（どんなに早く寝ても届かない） | 推奨就寝時刻は「区間内で低下率が最小になる時刻」とし、文面は「今夜は何時に寝てもベスト比 -◯% 程度の見込み。できるだけ早めに」に切り替える |
| 全区間で閾値を満たす | 区間の最も遅い端（起床4時間前）を採用せず、**平常時睡眠時間を確保できる時刻**を推奨する（過小睡眠を推奨しないため） |
| 現在時刻が既に区間の終端を過ぎている | 「今すぐ寝てください」とし、% は最小値を提示する |

### モデルの限界（明示すること）

これは母集団の生理モデルであり、本人の実測ではない。ver1.0 の % は目安である。この旨をメッセージ文面に含め、ガードレールで断定表現を弾く。夜のクイックリプライで蓄積した5段階評価が30日分たまった時点で、ver2 において係数を個人フィットさせる。

## 6. リカバリー算出（model/recovery.py）

### カフェイン

- 半減期を 5 時間として体内残存量をモデル化
- 今夜の推奨就寝時刻において残存量が閾値未満になる **最終摂取可能時刻** を算出
- 低下カーブの谷の手前に摂取タイミングを配置する
- **分割条件**: 起床時刻から最終摂取可能時刻までが 8 時間を超える場合は2回に分割（起床+1h と 谷の90分前）。8 時間以下なら1回のみ（起床+1h）

### 光曝露

- 起床後30分以内の屋外光曝露を推奨（概日位相の前進）
- 就寝の約3時間前から高照度・ブルーライトの回避を推奨
- 時刻はすべて個人の起床時刻・推奨就寝時刻から算出する

## 7. LLM の扱い（llm/）

- 呼び先: `POST https://api.openai.com/v1/chat/completions`（`urllib.request`）
- モデル: `LLM_MODEL` 環境変数。**既定値は暫定であり、実機確認時に正しい文字列へ差し替える**
- APIキー: Secrets Manager `sleeptech/openai`
- 役割: **確定した数値・時刻を日本語の文章に整形することのみ。** プロンプトに数値を埋め込み、変更を禁じる
- 温度: 0.7（表現の変化のため）。数値はプロンプト内の確定値であり温度の影響を受けない

### 障害時フォールバック（設計要件）

1. タイムアウトまたはエラー時は2回リトライ
2. なお失敗する場合、Python が保持する数値からテンプレート文を組んで送信する

**LLM が落ちても、推奨就寝時刻とリカバリー時刻は必ず届く。** モデルIDが未確定のまま実装を進める以上、この経路は必須である。

**テンプレート文にも夜のクイックリプライは必ず付与する。** 付与を怠ると LLM 障害が起きた晩のフィードバックが系統的に欠落し、ver2 のキャリブレーション用データに偏りが生じる。

## 8. ガードレール（guardrail/validator.py）

転用元の正規表現ベース検証を移植し、本プロジェクト向けに検査項目を差し替える。

| 検査 | 内容 |
|---|---|
| 医療断定 | 「診断」「治療」「病気です」等の医学的断定を弾く |
| 過度な不安煽り | 「取り返しがつかない」「寿命が縮む」等を弾く |
| 断定表現 | 「必ず」「確実に」＋% の言い切りを弾く（目安である旨の併記を必須とする） |
| 数値改変 | プロンプトで指示した数値・時刻が本文に正しく現れているかを照合。改変を検出したら再生成 |
| 人格否定 | 転用元の検査をそのまま維持 |

不通過時は最大2回まで再生成し、それでも通らなければ安全なテンプレート文へフォールバックする。

### 数値照合の実現方式

単純な文字列一致では日本語の表記ゆれ（`23:30` / `23時30分` / `午後11時半`）で誤検知が多発し、常にテンプレートへ落ちて LLM 文章化の価値が消える。**照合前に正規化する。**

1. 本文を正規化する: 全角数字→半角、`時`→`:`、`分`を除去、`午後N時`→`N+12:00`、`半`→`:30`
2. 正規表現で時刻トークン（`HH:MM`）と % トークン（`-?NN%`）を抽出
3. 抽出結果の集合が、プロンプトに埋め込んだ確定値の集合を **包含しているか** を検査
4. % は丸め誤差を許容せず完全一致（Python 側で整数に丸めてから渡すため）
5. 確定値に含まれない時刻・% が本文に現れた場合も不通過とする（LLM が数値を捏造した状態）

## 9. データモデル（DynamoDB）

単一テーブル設計。パーティションキー `pk`、ソートキー `sk`。

**エンティティ種別を pk に、日付を sk に置く。** baseline（直近14日）も睡眠負債（直近7日）も日付範囲クエリを必要とするため、日付は必ず sk 側でなければならない。

| エンティティ | pk | sk | 内容 |
|---|---|---|---|
| 日次バイタル | `VITAL` | `<date>` | 睡眠時間・深睡眠・REM・中途覚醒・HRV・皮膚温・呼吸数・夜間平均HR・体重 |
| 予測 | `PREDICT#NIGHT` / `PREDICT#MORNING` | `<date>` | 推奨就寝時刻、時間帯別低下率、リカバリー時刻 |
| メッセージ | `MSG#NIGHT` / `MSG#MORNING` | `<date>` | 本文、ガードレール結果、再生成回数、送信可否 |
| フィードバック | `FEEDBACK` | `<date>` | 5段階評価、回答時刻 |
| 設定 | `CONFIG` | `META` | 起床時刻の上書き値、目標低下率閾値 |
| 冪等フラグ | `IDEM#NIGHT` / `IDEM#MORNING` | `<date>` | 送信済みフラグ |

範囲取得は `Key("pk").eq("VITAL") & Key("sk").between(since, until)` で行う。GSI は不要（全アクセスパターンが pk 固定＋sk 範囲で満たせる）。

**既存の `dynamo_backend.py` は流用しない。** 既存は `PK="MEM#<namespace>", SK="<key>"` で値を `json` 属性に文字列格納する汎用 KV ストアであり、`query(namespace)` は namespace 内の全件を返すだけで sk 範囲指定ができない。日付範囲クエリを前提とする本設計とは非互換のため、`put` / `get` / `query_range` を持つバックエンドを新規に実装する。値を JSON 文字列でラップして Decimal 変換問題を避ける手法だけは踏襲する。

バイタルの保持期間は 365 日（TTL）。フィードバックは ver2 の学習に使うため無期限（TTL を設定しない）。

### フィードバックの取り込み

夜のクイックリプライは通常のテキストメッセージとして Webhook に届く。自然文と衝突しない固定形式を使う。

- クイックリプライの `action.text` を `評価:1` 〜 `評価:5` とする
- `WebhookFn` は `評価:` の前方一致のみで判定する（LLM 分類器は使わない）
- 紐付け先は **直近の未回答 `PREDICT#NIGHT`**。当日の夜メッセージ送信後であれば当日、それ以前なら前日を遡って最大2日分まで探す
- 該当が見つからない場合は保存せず、会話として応答する
- 同じ日付に複数回答が来た場合は最後の回答で上書きする

## 10. エラー処理

| 事象 | 挙動 |
|---|---|
| Google Health 取得失敗・睡眠データ欠損（朝） | **予測 % を一切出さない。** データ欠損である旨と一般的アドバイスのみ送信 |
| 履歴が3日未満（夜・初回起動時） | ベースラインを既定値（起床 7:00、睡眠 7時間30分）で仮置きし、予測は出す。ただし「まだデータが少ないため精度が低い」旨を文面に必ず含める |
| 履歴が3日以上14日未満（夜） | 取得できた日数だけで中央値を算出。既定値へのフォールバックは行わない |
| OpenAI API 障害 | 2回リトライ後、テンプレート文で送信（数値は保持されている） |
| 同意失効（`ConsentRevokedError`） | 収集を停止し、再認証を促す通知を送る |
| ガードレール不通過 | 最大2回再生成 → 安全なテンプレート文 |
| 二重実行 | `IDEM#NIGHT` / `IDEM#MORNING` の `<date>` で冪等制御 |

## 11. テスト

優先順位の高い順。

1. **ガードレール** — 医療断定・不安煽り・数値改変の検出（最優先・NON-NEGOTIABLE）
2. **`two_process`** — 境界値、単調性（睡眠が短いほど低下率が大きい）、線形スキャンの3つの境界ケース（解なし／全域可／時刻超過）、および **出力レンジの妥当性**。後者は第5節「パラメータ確定値」の期待出力表に対する検査とし、あわせて午後の低下率が午前を上回ることを検査する。ここが外れているとモデル係数が誤っている
3. **`recovery`** — カフェイン最終摂取時刻の境界、光曝露時刻の算出
4. **LLM 障害時フォールバック** — API 失敗時にテンプレート文が送信されること
5. **`baseline`** — 起床時刻中央値、データ不足時の既定値
6. **統合（夜／朝）** — フェイク注入による end-to-end

`model/` 配下は純粋関数のみで構成し、AWS も LLM も使わずにテストできる状態を保つ。
