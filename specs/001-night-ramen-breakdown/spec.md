# Feature Specification: Night Ramen Breakdown 自律改善ループシステム

**Feature Branch**: `001-night-ramen-breakdown`

**Created**: 2026-06-14

**Status**: Draft

**Input**: User description: "深夜のラーメン断ち自律改善ループシステム（spec-v4.md）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 夜の説得通知を受け取る (Priority: P1)

ユーザーは、夜食ラーメンの欲求が高まる時間帯（例: 22:00〜23:00）に、自分のバイタルデータに
裏付けられた「心に刺さる説得メッセージ」を通知で受け取る。メッセージは「昨夜ラーメンを食べた結果、
睡眠スコアがどう下がり、HRV や翌日の活動量にどう影響したか」を具体的に示し、思いとどまるよう促す。

**Why this priority**: これがシステムの中核価値であり、これ単体で「ラーメンを思いとどまる」という
本来の目的を最小限に達成できる MVP。他の機能はこの通知の質を高めるための支援機能である。

**Independent Test**: ダミーのバイタルデータと固定の目標設定を与えた状態で、夜間トリガーを発火させ、
ユーザーの通知UIに説得メッセージが届くことを確認できる。メッセージがデータに言及していれば価値達成。

**Acceptance Scenarios**:

1. **Given** 前夜の睡眠・自律神経データが収集済みで夜間トリガー時刻に達した、**When** システムが通知を発火する、**Then** ユーザーはバイタルデータに言及した説得メッセージを通知UIで受信する。
2. **Given** 説得メッセージが生成された、**When** メッセージが安全検証（ガードレール）を通過しなかった、**Then** ユーザーには安全なフォールバック文面が届くか、送信が見送られ、原文は送信されない。
3. **Given** 前夜のバイタルデータが未取得、**When** 夜間トリガーが発火する、**Then** システムはデータ欠損を検知し、一般的（非個別化）かつ安全な励まし文面を送るか送信を見送る。

---

### User Story 2 - 朝のバイタルデータ自動収集と記憶蓄積 (Priority: P1)

毎朝、システムはユーザーの健康データソースから前夜のバイタルデータ（睡眠・自律神経・代謝・呼吸・
体重・翌日の活動量）を網羅的に取得し、ユーザーの自己申告（昨夜ラーメンを食べたか）と紐づけて
長期記憶へ蓄積する。これにより「ラーメンの有無」と「身体への影響」の対応関係が時系列で積み上がる。

**Why this priority**: 説得メッセージ（US1）が個別化された説得力を持つための前提データ基盤。
これがなければUS1は一般論しか言えない。US1と並ぶP1。

**Independent Test**: 健康データソースの同意済みテストアカウントに対し朝の収集ルーティンを実行し、
当日分のバイタル指標と自己申告フラグが長期記憶に1レコードとして保存されることを確認できる。

**Acceptance Scenarios**:

1. **Given** ユーザーが健康データソースへのアクセスに同意済み、**When** 朝の収集ルーティンが実行される、**Then** 前夜の睡眠スコア・中途覚醒回数・深い睡眠時間・夜間平均心拍・HRV・皮膚温変化・呼吸数・翌朝の体重/体脂肪率・翌日の歩数/消費カロリーが取得され記憶に保存される。
2. **Given** ユーザーが昨夜の夜食ラーメン有無を申告した、**When** 朝の収集が走る、**Then** その Boolean 申告が当日のバイタルレコードに紐づけて記憶される。
3. **Given** 健康データソースの一部指標が取得できない、**When** 収集が走る、**Then** 取得できた指標のみ保存し、欠損は欠損として記録され、処理は失敗せず継続する。

### User Story 3 - 目標設定と達成率に応じた説得強度の自動調整 (Priority: P2)

ユーザーは定量的な目標（例: ラーメンを我慢できた日の割合=成功率85%、減量2kg）を設定できる。
システムは蓄積データから現在の達成率を評価し、達成状況に応じて説得メッセージの強度（穏やかな励まし
〜強い警告）を自動で調整する。目標に近づいていれば称賛寄り、遠ざかっていれば危機感を強める。

**Why this priority**: US1の説得をパーソナライズし長期的な行動変容を促す高度化機能。
MVP（US1+US2）の上に乗る最適化レイヤーのためP2。

**Independent Test**: 目標値と一定期間のダミー実績を与え、達成率が高いケースと低いケースで、
生成される説得メッセージの強度（トーン区分）が異なることを確認できる。

**Acceptance Scenarios**:

1. **Given** 成功率と減量の目標が設定済み、**When** システムが直近実績から達成率を評価する、**Then** 達成率が数値として算出され記録される。
2. **Given** 達成率が目標を大きく下回る、**When** 夜の説得メッセージを生成する、**Then** より危機感の強い（ただしガードレール範囲内の）トーンが選択される。
3. **Given** 達成率が目標を上回る、**When** 夜の説得メッセージを生成する、**Then** 称賛・維持を促す穏やかなトーンが選択される。

---

### User Story 4 - 説得アプローチの自律的な学習・改善 (Priority: P3)

システムは過去の説得履歴とその後の結果（翌日のラーメン有無・バイタル改善）を長期記憶から参照し、
「どの説得アプローチが効果的だったか」を踏まえて今夜の説得プロンプトを自律的に更新し続ける。
これにより、何が効くかが時間とともに洗練される。

**Why this priority**: システムの「自律改善ループ」としての真価だが、効果測定には一定の運用データ蓄積が
前提となり、初期から無くても MVP は成立するため P3。

**Independent Test**: 異なる説得履歴と結果のパターンを記憶に与えたとき、次回生成される説得プロンプトの
方針が履歴を反映して変化することを確認できる。

**Acceptance Scenarios**:

1. **Given** 過去の説得とその後の結果が記憶に蓄積されている、**When** 今夜の説得プロンプトを更新する、**Then** 効果的だった傾向を反映した方針でプロンプトが上書き更新される。
2. **Given** プロンプトが自律更新された、**When** 更新内容が安全検証を通る前、**Then** ガードレール検証を経て初めて記憶へ保存され、検証不合格の更新は破棄される。

---

### Edge Cases

- **データ全欠損の夜**: 前夜・当日のバイタルが一切取得できない場合、個別化説得は行わず、一般的で安全な
  メッセージにフォールバックするか送信を見送る（無根拠な断定をしない）。
- **ガードレール連続不合格**: 生成メッセージが規定回数連続で検証に落ちた場合、その夜は固定の安全文面に
  切り替え、無限ループや無通知を避ける。
- **同意の取り消し**: ユーザーが健康データソースへのアクセス同意を取り消した場合、以後の収集を停止し、
  既存個別化を停止する。
- **重複通知**: 同一夜にトリガーが多重発火しても、ユーザーへの説得通知は1晩あたり既定回数を超えない。
- **目標未設定**: 目標が未設定の場合でも US1/US2 は機能し、強度調整（US3）は中立トーンを既定とする。
- **極端なバイタル値**: 異常値（測定エラー由来と思われる値）は分析から除外または平滑化し、誤った断定を避ける。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは毎朝決まったタイミングで、ユーザーの健康データソースから前夜の網羅的なバイタルデータを取得しなければならない（MUST）。
- **FR-002**: システムは取得したバイタルデータを、ユーザーの夜食ラーメン有無の自己申告（Boolean）と紐づけて長期記憶に永続化しなければならない（MUST）。
- **FR-003**: システムは収集すべきバイタル指標として、睡眠スコア・中途覚醒回数・深い睡眠時間・夜間平均心拍・心拍変動(HRV)・睡眠中の皮膚温変化・呼吸数・翌朝の体重/体脂肪率・翌日の総歩数/消費カロリーを対象としなければならない（MUST）。
- **FR-004**: システムは蓄積データから、夜食ラーメンが睡眠品質・自律神経・代謝・呼吸・翌日の活動量に与えた悪影響を推論し数値化しなければならない（MUST）。
- **FR-005**: ユーザーは定量的目標（成功率・減量目標など）を設定でき、システムはその達成率を評価しなければならない（MUST）。
- **FR-006**: システムは達成率に応じて説得メッセージの強度を自動調整しなければならない（MUST）。
- **FR-007**: システムは夜間の指定時間帯に、個別化された説得メッセージをユーザーの通知UIへ送信しなければならない（MUST）。
- **FR-008**: システムはユーザーへ送信する全メッセージを、送信前にガードレール検証へかけなければならない（MUST）。検証は最低限、(a)差別的/不適切表現の不在、(b)仕様ルール・目標からの逸脱の不在、(c)人格否定・過激な罵倒・モチベーションを完全に喪失させる「正論の暴力」でないこと、を確認する。
- **FR-009**: システムはガードレール検証に不合格のメッセージを送信してはならない（MUST NOT）。不合格時は安全なフォールバックへ差し替えるか送信を見送る。
- **FR-010**: システムは過去の説得履歴とその後の結果を参照し、説得アプローチを自律的に更新しなければならない（MUST）。更新後のプロンプトはガードレール検証を通過した場合にのみ記憶へ保存される。
- **FR-011**: システムは機微な健康データおよび認証情報を、平文でログ出力・ソース埋め込みしてはならない（MUST NOT）。
- **FR-012**: システムはユーザーが健康データソースへのアクセス同意を取り消した場合、以後の自動収集を停止しなければならない（MUST）。
- **FR-013**: システムは自律ループの各ステップ（収集・分析・目標評価・プロンプト更新・通知）の実行を追跡可能な形で記録しなければならない（MUST）。
- **FR-014**: システムは1晩あたりのユーザーへの説得通知回数を既定の上限内に制限しなければならない（MUST）。
- **FR-015**: システムはバイタルデータが欠損または異常な場合に、無根拠な断定を避け、安全側のメッセージにフォールバックしなければならない（MUST）。

### Key Entities *(include if feature involves data)*

- **デイリーバイタルレコード**: ある日付に対する1日分の記録。睡眠・自律神経・代謝・呼吸・体重・翌日活動量の各指標と、夜食ラーメン有無の自己申告フラグを保持する。時系列で蓄積される。
- **目標 (Goal)**: ユーザーが定義する定量的指標。成功率の目標値、減量目標値などを保持し、達成率評価の基準となる。
- **説得メッセージ履歴**: 各夜に生成・送信（または見送り）されたメッセージ本文、選択された強度トーン、ガードレール検証結果、送信日時を保持する。後続の効果測定と学習に用いられる。
- **説得プロンプト（戦略）**: エージェントが説得メッセージ生成に用いる現行方針。自律ループにより更新され、検証通過版が記憶に保存される。
- **分析結果**: ラーメンが各バイタル指標に与えた悪影響の推論・数値化結果。説得メッセージの根拠として参照される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 朝の収集ルーティンは、同意済みユーザーについて対象バイタル指標の取得を毎日成功させ、欠損なく取得できた日が運用日の90%以上である。
- **SC-002**: 夜間の説得通知は、指定時間帯（例: 22:00〜23:00）に1晩あたり既定回数以内で確実に届き、配信成功率が95%以上である。
- **SC-003**: ユーザーへ送信される説得メッセージのうち、ガードレール検証を経ずに送信されたものは0件である（検証通過率100%）。
- **SC-004**: 送信される個別化説得メッセージの90%以上が、当該ユーザーの実際のバイタルデータ（睡眠・HRV・活動量等）に具体的に言及している。
- **SC-005**: 運用開始から一定期間（例: 8週間）で、ユーザーの夜食ラーメン我慢成功率が設定目標に対し改善傾向（運用前ベースライン比で向上）を示す。
- **SC-006**: 機微な健康データ・認証情報がログや成果物に平文露出した事象が0件である。

## Assumptions

- 対象ユーザーは単一個人（本人）であり、マルチテナント運用は本バージョンのスコープ外とする。
- ユーザーは健康データソースへのアクセスに事前同意し、テストユーザーとして同意が明示管理されている。
- 夜食ラーメンの有無はユーザーの自己申告に依存し、申告がない日は「未申告」として扱う。
- 通知UIはユーザーが日常的に確認する単一チャネルを利用し、双方向の対話は本バージョンでは必須としない。
- バイタルデータの保持期間は分析・学習に必要な範囲とし、業界標準的なプライバシー慣行に従う。
- 説得メッセージの「効果」は、翌日の自己申告とバイタル改善を代理指標として測定する。
- 初期開発段階ではコスト最小の言語モデル設定を用い、本番では分析用・生成用に役割別のモデルを用いる（モデル選択は構成で切替可能）。
