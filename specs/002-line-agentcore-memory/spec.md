## 概要

既存の Night Ramen Breakdown に、LINE 上での自由対話機能を追加する。ユーザーが Bot に話しかけると、
エージェントが「過去の会話」と「ユーザー自身のバイタル傾向・ラーメン履歴」を踏まえて、文脈を理解した
パーソナルな応答を返す。会話は長期記憶に蓄積され、日をまたいでもユーザーのことを覚えている。
従来の固定的な「食べた/我慢した」入力を、自然な会話の中での申告に進化させる。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 文脈を覚えた自由対話 (Priority: P1)

ユーザーは LINE で Bot に自由に話しかけられる（例「今日は疲れた」「昨日はよく眠れた気がする」）。
Bot は過去の会話の流れと、ユーザーのバイタル傾向（睡眠・HRV・ラーメン履歴）を踏まえ、
励ましや具体的なアドバイスを含むパーソナルな返答をする。会話は記憶され、後の対話に引き継がれる。

**Why this priority**: 「対話ができるようにする」という今回の中核要求。これ単体で価値が成立する MVP。

**Independent Test**: テスト用ユーザーで複数ターンの会話を行い、(a)前のターンの内容を踏まえた応答が返る、
(b)別セッションでも以前学習した事項に言及できる、ことを確認できる。

**Acceptance Scenarios**:

1. **Given** ユーザーが過去に Bot と会話している、**When** 新たに話しかける、**Then** Bot は過去の文脈を踏まえた応答を返す。
2. **Given** ユーザーのバイタル履歴が蓄積されている、**When** 体調について尋ねる、**Then** Bot は実際のデータ傾向に触れた応答をする。
3. **Given** Bot が応答を生成した、**When** その応答が安全検証（ガードレール）を通過しない、**Then** 安全なフォールバック応答に差し替えられ、危険な応答は送信されない。

---

### User Story 2 - 会話からの自己申告抽出 (Priority: P1)

ユーザーが会話の中で夜食ラーメンの有無に言及すると（例「昨夜はラーメン我慢できた」「つい食べちゃった」）、
システムはそれを当日の自己申告として正確に記録する。明示的なコマンド入力は不要。

**Why this priority**: 既存の収集・分析ループ（翌朝の紐づけ）に会話を接続する要。US1と並ぶP1。

**Independent Test**: 会話で「食べた/我慢した」に相当する発話を行い、当日の申告レコードが正しい真偽値で記録されることを確認できる。

**Acceptance Scenarios**:

1. **Given** ユーザーが会話で「昨夜ラーメンを我慢した」と述べる、**When** メッセージが処理される、**Then** 当日の自己申告が「我慢（false）」として記録される。
2. **Given** ユーザーが「食べちゃった」と述べる、**When** 処理される、**Then** 当日の申告が「食べた（true）」として記録され、Bot は記録した旨と励ましを返す。
3. **Given** 発話がラーメンの有無を判別できない、**When** 処理される、**Then** 申告は記録されず、通常の対話応答が返る。

---

### User Story 3 - 長期記憶によるユーザー理解の蓄積 (Priority: P2)

システムは会話を重ねるごとに、ユーザーの嗜好・傾向・経緯（例「夜勤明けに食べたくなる」「励ましより
データで示す方が響く」）を長期記憶として学習し、以降の対話・夜の説得メッセージの質を高める。

**Why this priority**: 対話を一過性で終わらせず継続的にパーソナライズする高度化。MVP（US1/US2）の上に乗る。

**Independent Test**: 嗜好を示す会話を複数行った後、後日のセッションでその嗜好を反映した応答が返ることを確認できる。

**Acceptance Scenarios**:

1. **Given** ユーザーが過去の会話で特定の嗜好を示した、**When** 後日対話する、**Then** Bot はその嗜好を踏まえた応答をする。
2. **Given** 長期記憶に学習事項が蓄積されている、**When** 夜の説得メッセージを生成する、**Then** その学習を反映した説得が行われる。

---

### Edge Cases

- **応答遅延**: 記憶の取得と応答生成に時間がかかり、通知UIの応答受付時間を超えそうな場合、簡潔な応答にフォールバックする。
- **記憶が空**: 初回ユーザー（会話・履歴なし）でも、一般的だが安全で親切な応答を返す。
- **危険・不適切な応答**: 生成応答がガードレールに不合格なら送信せず安全文面へ（原則II / 既存ループと同一の安全基準）。
- **なりすまし**: 対話の入口（Webhook）は正規の送信元のみ受け付ける（署名検証）。
- **長文・連投**: 過度に長い入力や短時間の連投でも、システムは破綻せず応答するか丁寧に制限を伝える。
- **記憶の取り違え**: 別ユーザーの記憶が混ざらないよう、記憶はユーザー単位に厳密分離される。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-101**: システムはユーザーが通知UI（LINE）で送った自由文メッセージを受け取り、対話応答を返さなければならない（MUST）。
- **FR-102**: システムは過去の会話履歴を記憶し、後続の応答に文脈として反映しなければならない（MUST）。
- **FR-103**: システムは会話を重ねてユーザーの嗜好・傾向を長期記憶として学習し、セッションをまたいで参照できなければならない（MUST）。
- **FR-104**: 対話応答は、ユーザーの実際のバイタル傾向・ラーメン履歴を文脈として活用できなければならない（MUST）。
- **FR-105**: システムは会話中の夜食ラーメン言及を解釈し、当日の自己申告（真偽）として記録しなければならない（MUST）。固定キーワードパースと会話エージェント抽出を**併用**し、固定パースが判別不能のとき会話抽出で補完する。判別不能時は記録しない。
- **FR-112**: 会話エージェントは健康コーチとして振る舞い、睡眠・体調・夜食ラーメンに焦点を当て、話題が逸脱した場合は本題へ自然に戻さなければならない（MUST）。
- **FR-106**: ユーザーへ返信する全応答は、送信前にガードレール検証（差別/不適切・仕様逸脱・人格否定や過激な罵倒の不在）を通過しなければならない（MUST）。不合格応答は送信してはならない（MUST NOT）。
- **FR-107**: 記憶はユーザー単位で厳密に分離され、他ユーザーの記憶が混入してはならない（MUST NOT）。
- **FR-108**: 対話の受信入口は正規の送信元のみを受理しなければならない（MUST、署名検証）。
- **FR-109**: システムは機微な健康データ・認証情報を平文でログ出力・ソース埋め込みしてはならない（MUST NOT）。
- **FR-110**: 既存の朝の収集・夜の説得ループは、会話から記録された自己申告と長期記憶を活用できなければならない（MUST）。
- **FR-111**: システムは応答生成に時間がかかる場合でも、通知UIの受付制限内に応答するか、簡潔な代替応答を返さなければならない（MUST）。

### Key Entities *(include if feature involves data)*

- **会話ターン**: ユーザー/Bot の各発話。送信者・本文・時刻を持ち、ユーザー単位・セッション単位で記憶される（短期記憶）。
- **長期記憶レコード**: 会話から抽出されたユーザーの事実・嗜好・要約。ユーザー単位の名前空間で保持され、意味検索で参照される。
- **会話由来の自己申告**: 会話から抽出された当日の夜食ラーメン有無（既存の自己申告エンティティと同一の意味）。
- **対話セッション**: 一連の会話のまとまり。ユーザー識別子と関連づく。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: ユーザーがLINEで送ったメッセージに対し、95%以上で文脈に沿った応答が返り、配信される。
- **SC-102**: 直前のターンの内容を踏まえた応答が、複数ターン会話の90%以上で確認できる。
- **SC-103**: ユーザーへ返信される応答のうち、ガードレール検証を経ずに送信されたものは0件である。
- **SC-104**: 会話でラーメンの有無を明確に述べた場合、90%以上で正しい真偽値の自己申告が記録される。
- **SC-105**: 後日の新セッションで、以前学習したユーザーの嗜好・事実に言及できるケースが確認できる（長期記憶の有効性）。
- **SC-106**: 機微な健康データ・認証情報がログや成果物に平文露出した事象が0件である。
- **SC-107**: 通常応答の配信が、ユーザー送信から妥当な時間（例: 10秒）以内に行われる。

## Assumptions

- 対象ユーザーは単一個人（本人）。マルチテナントはスコープ外だが、記憶はユーザー識別子で分離する設計とする。
- 会話の入口・出口は既存の LINE チャネル（Webhook 受信・返信）を用いる。
- 長期記憶の基盤として agentcore Memory を採用する（ユーザー要件）。バイタル時系列・冪等・目標などの厳密な
  構造化データは既存の DynamoDB に残す（agentcore Memory はセマンティック検索向きで厳密な数値範囲取得・原子的冪等に不向きなため）。
- 会話応答に用いるモデルは応答速度・コストを考慮して選択し、構成で切替可能とする。
- 長期記憶の抽出は非同期・結果整合で行われうるため、即時反映を前提としない。
- 安全基準は既存ループと同一（Constitution 原則II）。会話応答もガードレール対象。
